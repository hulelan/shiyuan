写给接手这件事的人。前面已经查清的、已经备好的、以及几处会绊人的地方，都在这里。
**导入这一步的代码尚未写**：名单和事实齐了，脚本没有。

## 零、这件事要解决什么

一句话：**站上没有《长恨歌》，没有《琵琶行》，没有《念奴娇·赤壁怀古》，
苏轼只有一篇，陆游辛弃疾一篇都没有。** 这件事就是把这些补上。

不是排序问题，不是推荐问题，不是标注问题 —— 是**这些作品压根不在库里**。
当初导入取的是上游文件开头的若干条，取到哪儿算哪儿，于是唐诗那两千篇有
三分之二是宫廷祭祀乐章，太宗皇帝 101 篇而白居易 18 篇。

做完之后，其它一切才谈得上：相似度再准，也推不出库里没有的诗；
检索排序再好，搜《琵琶行》也还是零条。

## 三、一个关键发现：上游自带热度排名

`rank/poet/poet.tang.rank.*.json`、`rank/poet/poet.song.rank.*.json`、
`rank/ci/ci.song.rank.*.json` —— 336 个文件、332,909 条，与诗文一一对应。每条形如：

```json
{"author":"太宗皇帝","title":"帝京篇十首 一","baidu":20600,"google":50400,"bing":157000,"so360":1120,"bing_en":97600}
```

**这就是挑篇目的依据。** 同一位诗人取哪 60 首，不必凭印象，也不必再跑模型：
按搜索热度取前 N。join 用 `(author, title)`；上游是繁体，须 `opencc t2s` 转换后再对。

两条使用上的注意：

- **不要把五个引擎的点击数加起来。** 那是五个口径不同、各自不稳定的估计值，
  加总之后，某一个引擎给出的大数就能单独决定名次。
  改成**各引擎内先排名次，再取中位名次** —— 序数稳，量级不稳。
- **这是"今人找不找"的尺子，不是"历不历史重要"的尺子。** 搜索热度大体反映的是
  中小学课本与流行选本。本文件的目标写的就是"读者会去找谁"，那么这把尺子是对的；
  但要在文档里说明白，免得日后有人把这份名单当成别的意义上的正典。

## 四、动手的顺序

1. 写 `tools/import_canon.py`：
   - 读 `canon_poets.json` 与三套上游文件（唐诗 / 全宋诗 / 宋词）；
   - **先归一标题**，再做 rank 的 join、再计入 cap
     （用 `tools/relevance_lib.py` 的 `clean_title()`，理由见第五节）；
   - 用 rank 的中位名次排序，每位取 cap 篇，扣掉本站已有的；
   - 繁转简、生成拼音（`pypinyin`，用仓库的 `.venv`）；
   - 按 `tools/corpus_lib.py` 的 SOURCE_FIELDS 写成 jsonl，并入 `data/source/`；
   - **两道去重**：先按 `stable_id`（即 `作者|标题|去空白原文`）挡住完全相同的，
     再用 `relevance_lib.overlap()` 挡住字面高度重合的 —— 只有第一道是不够的，
     理由见第五节。
2. `./.venv/bin/python tools/build_site_data.py` —— 重建 `data/site/`。
   这一步会把卡片、索引分片、作者聚合、字词索引、时间轴全部重算；
   **不必**再单独跑 `rebuild_timeline.py`，那个脚本是给"只改了年份"的场合用的。
3. `./.venv-ml/bin/python tools/embed_corpus.py` —— 重算语义向量（约 6 分钟，需 GPU）。
4. `./.venv/bin/python tools/build_relevance.py` —— 重算「与此篇相近」与 BM25 检索索引。

   第 3、4 步不能省。`build_site_data.py` 会保住 `near/` 与 `bm25/` 两个目录，
   并在 manifest 里标 `relevanceStale: true`、打印重算命令 —— 也就是说漏跑不会报错，
   只是相似度和检索排序悄悄用着旧语料算的结果。新导入的两千多篇不会有邻居。

5. 新篇目没有译文/注释/赏析，要 `tools/enrich_glm.py` 才有。
   先 `--dry-run` 看清单与预估。按当前模型的价钱（约 \$1.7/1000 首），
   2,331 篇约 \$4；连同现存的 1,336 篇欠账一起补，约 \$6。
   可以分批，也可以先让新篇目只有原文 —— 但要知道代价：
   编辑层同时也是「与此篇相近」的一路信号，没有译文赏析的篇目邻居明显更松。

## 五、几处会绊人的地方

- **`MAX_CHARS = 360` 把长诗滤掉了**（`tools/build_corpus.py:48`）。《长恨歌》
  《琵琶行》《茅屋为秋风所破歌》不在库里就是因为这一条，不是因为没导。
- **`build_site_data.py` 会先清空 `data/site/`** 再重建（KEEP 之外的都删）。跑之前
  确认 `data/enrich/` 是全的 —— 译文都在那里，site 只是产物。
- **时间轴的年份有三种底子**：逐篇断代 / 按作者估算 / 只知朝代。占位年份一律不进
  直方图，否则整个朝代堆在同一格。改 `build_site_data.py` 里那段，记得同步改
  `tools/rebuild_timeline.py`。
- **不要去爬古诗文网 / 古文网的译文、注释、赏析** —— 那是有版权的编辑成果。原文
  是公有领域，chinese-poetry 也是自由许可的，导入正文没有问题。
- 上游 `全唐诗/` 目录里同时装着 `poet.song.*`（全宋诗），别被目录名骗了。

- **乐府栏目名混在标题里，会吃掉 cap，也会让 rank 对不上。**
  《全唐诗》的乐府部分把栏目名写进了诗题：本站现有唐诗 2,142 篇，其中
  **1,441 篇（67%）** 带 `杂曲歌辞 ` `相和歌辞 ` `郊庙歌辞 ` 这类前缀。
  同一首诗因此在上游有两条记录、两条 rank：《杂曲歌辞 蜀道难》与《蜀道难》。
  不归一就直接照名单取，李白那 90 篇的额度会有一部分花在自己的副本上。
  `tools/relevance_lib.py` 的 `clean_title()` 就是干这个的（它同时也剥词牌名）。

  注意区分：**同题不同作者是正常的**，不要一并合掉 ——
  《相和歌辞 长门怨》有 17 位作者各写一首，《横吹曲辞 折杨柳》有 13 位。
  `(author, title)` 这个键本身分得开它们，要归一的只是标题里的栏目名。

- **只按 `作者|标题|原文` 去重是不够的。** 那是 `stable_id` 的定义，只挡得住
  一字不差的重复。真正在库里的重复长这样（全库 125 对，涉及 240 篇，
  清单在 `data/dupes.tsv`）：

  | 情形 | 例子 |
  |---|---|
  | 乐府栏目重出 | 《杂曲歌辞 蜀道难》李白 ←→ 《蜀道难》李白 |
  | 精编与导入撞车 | 《江雪》柳宗元（精编）←→ 《江雪》柳宗元（导入）|
  | 归属存疑 | 《行宫》元稹 ←→ 《故行宫》王建 |
  | 传本异文 | 《静夜思》"床前明月光" ←→ "床前看月光" |

  这四类的原文都不是一字不差，`stable_id` 一条也挡不住。
  `relevance_lib.overlap()` 算的是二元组覆盖率，四类都认得出。
  语料要扩到八倍，这道闸得在导入时就装上，否则同一个问题按比例放大。

  顺带一说：这 125 对**现在就该清一轮**，不必等导入。哪一条留、哪一条删
  是编辑判断（《赤壁》该挂杜牧还是李商隐、《静夜思》两个传本要不要都留），
  脚本不替人决定，所以只出清单。
